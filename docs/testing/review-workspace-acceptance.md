# Review workspace container acceptance

The opt-in `CI` workflow input `review_workspace_acceptance` builds `sandbox/Dockerfile` from the dispatched revision, installs gVisor with the supported worker flags, and runs the production Docker provider against that image. Dispatch the complete stack's feature branch: the cold path must include workspace lifecycle integration. Workflow dispatch does not deploy that branch.

The job fails when Docker, the explicit image, the scoped network, Linux, or `runsc` is unavailable. It never substitutes mocked exec, host Git execution, or the standard `runc` runtime for container acceptance. Ordinary Go suites skip the container suite; a requested Make target cannot skip it.

```sh
docker build --label "org.opencontainers.image.revision=$(git rev-parse HEAD)" -t review-acceptance:local -f sandbox/Dockerfile .
docker network create review-acceptance-local
REVIEW_ACCEPTANCE_IMAGE=review-acceptance:local \
REVIEW_ACCEPTANCE_NETWORK=review-acceptance-local \
REVIEW_ACCEPTANCE_RUNTIME=runsc \
REVIEW_ACCEPTANCE_RUNSC_VERSION="$(runsc --version | head -n 1)" \
REVIEW_ACCEPTANCE_SOURCE_SHA="$(git rev-parse HEAD)" \
REVIEW_ACCEPTANCE_ARTIFACT_DIR="$(mktemp -d)" \
make test-review-container-acceptance
```

The runtime must already be installed and registered. On a disposable Linux host, use the package source and `runsc install -- --ignore-cgroups --host-uds=open` invocation from `deploy/scripts/bootstrap.sh`. The hosted job performs that setup and removes only containers attached to its own network.

The acceptance cases use isolated synthetic repositories with divergent captured base/head/merge-base commits, filtered file transport, actual offline Go vendoring, and actual locked npm installation. They exercise:

- Cold materialization with local reads of all captured trees and a version 2 evidence receipt.
- Warm reuse without installation or token lookup.
- A real `DockerProvider.Snapshot` followed by destruction, creation, and `RestoreForReviewPreparation`; source, dependency roots, and receipt survive that transport.
- The original eight-minute preparation budget, with queue time leaving a short remainder. All stages retain the same absolute deadline and the recipe process group stops before container destruction.
- Expired preparation with bounded platform-only verification: no setup, arbitrary repository verifier, token lookup, or receipt replacement.
- Rejection and cleanup for unsafe Git configuration, present packed-object corruption, and an explicit recipe failure.
- Absence of a synthetic private input from inspected creation environments, actual Docker exec argv/environments, provider logs, Git configuration, receipts, and Linux recipe process ancestry.

Before container destruction, the deadline case records the recipe PID and every observed member of its process group from Linux `/proc`. An absent process or an observed terminal `Z`/`X` state counts as stopped; every live or unknown state fails. This distinguishes stopped children retained as zombies by container PID 1 from running children.

The job uploads bounded per-scenario JSON and logs even when a scenario fails. JSON identifies the source SHA, image ID, operating system, architecture, Docker and gVisor versions, runtime, resource limits, elapsed times, token counts, receipt hash, and cleanup observations. The fixture-building test runs separately during ordinary host verification; its success is not container acceptance.

File transport does not prove live HTTPS authentication. Synthetic dependency and source fixtures do not accept a production repository recipe or establish the largest repository's hashing cost. Disk quotas, deployed image identity, worker network policy, and deployment are separate rollout evidence. Keep exact repository inventory and rollout evidence in the private infrastructure checkout.

The `cleanup_signal_failure` case injects a synthetic TERM permission error only for the recorded long-running recipe group. It requires the real KILL attempt and terminal cleanup guidance while preserving the original preparation deadline, then verifies a regular container-local quarantine marker and no live group member before destruction. This checks error handling in the actual runtime; natural Linux permission-denial reachability is not asserted.

## Private repository acceptance

`make test-review-real-repository-acceptance` runs a separate opt-in suite against pinned GitHub PR comparisons. Run it in private CI or on a private disposable Linux host. Supply the image, network, runtime, runtime version, image source SHA, and private artifact directory through the same `REVIEW_ACCEPTANCE_*` variables above. Also provide:

- `REVIEW_REAL_REPO_MANIFEST`: absolute path to a private JSON inventory.
- `REVIEW_REAL_REPO_RESOLV_CONF`: absolute path to a regular host resolver file with upstream nameservers reachable from the scoped network. The production provider mounts it read-only; gVisor cannot use Docker's embedded `127.0.0.11` resolver.
- `REVIEW_REAL_REPO_TOKEN_FILE`: path to a host-only regular file containing a read-scoped GitHub token, with permissions `0600`. Symlinks and oversized or multiline credentials are rejected. The harness never injects this file or token into container creation environments.

The version 1 manifest contains a `repositories` array. Each entry requires a unique artifact `name`, `full_name`, canonical credential-free HTTPS `clone_url`, `default_branch`, trusted `installation_id`, `token_kind` (`github_app_installation` or `github_actions_job`), `pr_number`, exact 40-character `base_sha` and `head_sha`, `config_sha256`, a `helper_sha256` path-to-hash map, `cpu_limit`, `memory_limit_mb`, `disk_limit_gb`, and `snapshot_limit_bytes`. Helper paths must remain under `.143/`. Use actual private inventory values; never commit the manifest or its results here. The suite follows inventory order sequentially so the largest repository can run first without sibling test contention.

Pin the recipe comparison separately from the platform image source. A retained merged recipe PR can be a preparation fixture when its exact head ref, captured base provenance, config/helper hashes and lock inputs are verified. The preparation engine still fetches and checks that live PR head; this does not exercise open-PR scheduling or publication. Do not push the selected comparison head while its trials are queued or running. A head-mismatch rejection is a failed repetition, even if the new commit changes documentation only; rebind explicitly and capture fresh results.

A cold run calls `PrepareCodeReviewWorkspace` with the original job creation time. Container creation, real HTTPS clone/fetch, captured-tree hydration, exact recipe setup, receipt creation, and the first local source read must fit the same eight-minute allowance. The suite checks the captured comparison, recipe and helper hashes, and unchanged tracked files. It then checks active warm reuse, streams a bounded real snapshot to a private temporary file, destroys the original container, restores into a new container, and checks reuse again. Container creation, restore transport, and restored verification share one original eight-minute turn budget. Finally, expired evidence must pass platform-only verification within 60 seconds with no installation, repository verifier, authenticated Git, token lookup, repair, or receipt replacement.

An observation-only decorator around the trusted controller records fixed stage labels, timings, and child process-group identities. It preserves the original functions, private stdin payload, recipe commands, security guards, deadlines, cleanup, return values, and exceptions. The reports distinguish full object hashing, tree closure, repository setup, and repository verification. Before each container is destroyed, the suite checks that every observed group has no live member. The observer adds measurement overhead; it never grants more preparation time. Destruction attempts retain bounded sanitized fixed-stage timings even when preparation fails before returning its container; no raw command or environment text is accepted by that trace decoder. Each kernel-verified container also has a host-only 500 ms memory sampler with a 45-minute cap. It retains a fixed-size aggregate of owned-cgroup byte and event maxima, sample counts, and explicit unavailable fields. Before destruction, Docker state is reduced to numeric/Boolean fields and fixed classifications, and the sampler is cancelled and joined. Previously observed counters survive disappearance of the cgroup; absent observations or zero earlier OOM counters never establish that no OOM occurred.

Normal and profiled runs also attempt a bounded 8 KiB owned `memory.stat` read, retaining only `anon`, `file`, `shmem`, `file_mapped`, `file_dirty`, `file_writeback`, `slab` and `kernel`. Missing or malformed data remains explicitly unavailable; separate stat coverage does not change completeness of the original required memory counters. In addition to independent field maxima, a fixed-size vector retains values from the first sampling pass with the largest observed `memory.current`. It never borrows an earlier vector when that pass lacks stat data. These sequential reads are not an atomic kernel snapshot. The fields overlap and must not be summed: `shmem` is included in `file`, and slab contributes to kernel memory. In gVisor, guest application memory uses shared backing, so `file` alone does not establish reclaimable filesystem cache; see the [runtime resource model](https://gvisor.dev/docs/architecture_guide/resources/).

For setup attribution only, `REVIEW_ACCEPTANCE_PROFILE_SOURCE_HELPER=1` enables a test-only observer for the exact supported streaming helper hash. Changing helper bytes requires an explicit observer audit and repin before new diagnostics. It preserves the original controller script and authentication-release check, intercepts only the fixed helper invocation at child launch, and invokes the original entry point with unchanged arguments, results, exceptions and deadlines. The inventory wrapper stays lazy, counts yielded files and records interrupted closure as incomplete work; the receipt wrapper observes the actual streaming function and its returned count. It does not patch global `Path` or JSON functions. Receipt work encloses inventory, so their timings and active memory observations overlap and cannot be added. Fixed phase/category labels retain numeric counts, byte totals and timings without another source inventory. A bounded decoder retains fixed-size aggregates and active counts; malformed diagnostic records invalidate diagnostics while output continues draining. Completed operation durations are worker time rather than phase wall time. Active samples describe shared container usage, and lifetime `memory.peak` cannot be assigned to a phase. Unfinished phases retain their active counts without inventing a duration. Profiling remains diagnostic-only; fresh acceptance repetitions omit the flag and retain the original eight-minute and 60-second limits.

Results include actual image/runtime/resource identities, Git and language-tool versions, source/evidence counts and sizes, full-hash and stage timings, cumulative container resource usage, snapshot size/hash and transport time, original deadlines, token counts, receipt identity, and destruction receipts. Full SDK argv/environment and provider-log streams are scanned for the host token and encoded forms; retained provider logs remain capped at 64 KiB and are withheld if a credential is detected. All result files are private. Raw snapshots use private temporary storage outside the uploaded artifact directory and are removed after partial writes, close failures, restore, or later test failures. Reports retain only bounded snapshot metadata. Declared executable tool hashes and modes are captured after cold setup and before restored engine execution, so automatic repair cannot hide tool loss. Healthy warm, restored, and expired reuse must not install or repair tools.

Before repository work, every real-repository container must prove its exact running host PID belongs to its owned cgroup v2 container group with finite `memory.max` and `cpu.max` matching the requested memory and CPU bounds. Shared service groups, unlimited values, redirected or missing kernel paths, and changed PID membership fail acceptance. Docker creation settings and guest resource statistics alone do not establish enforcement. The disk limit must be positive, requires actual Docker storage quota support, and fails closed if it is unavailable. A GitHub Actions job token can establish real private HTTPS transport for that job's repository; it does not establish deployed GitHub App token issuance. This suite performs the first local source read without invoking an LLM reviewer or publishing a durable workspace. Deployed image/network policy, production auth issuance, recipe publication and owner acceptance remain separate gates.

For disposable GitHub-hosted Linux jobs, `.github/scripts/prepare-review-acceptance-runtime.sh` provisions an owned Docker daemon on a physically reserved 24 GiB XFS filesystem with project quotas. It requires a separate 8 GiB reserve and, after image construction, at least 12 GiB free inside XFS so the full 10 GiB container quota retains metadata headroom. Its `--probe-quota` mode checks these reserves and confirms actual write exhaustion with a small disposable container. The owned daemon explicitly uses cgroup v2 with Docker's `cgroupfs` driver and runsc's filesystem cgroup management; it retains `--host-uds=open` and does not bypass cgroups. This is a disposable acceptance profile, not an automatic production daemon change. The owned daemon has no default bridge: build the sandbox image with `docker build --network=host`, then create the uniquely named acceptance network for test containers. Always invoke `.github/scripts/cleanup-review-acceptance-runtime.sh` after removing private credentials; it verifies daemon and loop-device ownership and preserves backing storage when that ownership cannot be established. On hosts using a systemd loopback resolver stub, setup selects the configured upstream file and fails if no usable configured server exists. Private resolver evidence records that selection without asserting reachability. The setup also retains bounded `runsc flags` output and the owned runtime registration. This command describes compiled defaults; those observations do not prove a running container's effective overlay medium. Optional execution/timeout/output-limit failures are explicit and do not change runtime settings. These scripts refuse local and self-hosted environments.

The real-repository Make target has a 45-minute suite timeout. A disposable job must leave additional time for setup, credential removal, owned-resource cleanup, and bounded artifact retention; its outer job timeout must exceed the suite timeout. This does not extend any individual preparation or verification deadline. Cleanup steps must tolerate initialization that failed before environment paths were exported. Retain at most 64 KiB of the owned daemon log, alongside its original byte count and retention limit.
