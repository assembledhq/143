# Design: GitHub rate-limit recovery

> **Status:** Partially Implemented | **Last reviewed:** 2026-09-15

Implementation plan for [VIR-161](https://linear.app/assembledhq/issue/VIR-161/investigate-recurring-github-rate-limiting). Prepared against repository revision `eb4da2211b3511f6143039a6ed8dd5f2ac0f3856`. The local PR 1-3 scope is implemented in the isolated worktree; production configuration, deployment, and rollout remain separate, unauthorized follow-ups.

## Purpose

When GitHub throttles an installation, stop avoidable requests, preserve queued reviews, and resume them automatically if GitHub recovers within the bounded recovery window. When that window expires, retain the existing actionable failure and manual review retry; do not silently re-enqueue a fresh job to bypass the bound. Keep review publication and merge safety checks authoritative. Reduce additional API demand only where measurements identify a worthwhile source.

We can implement and test the recovery changes without production access. We cannot yet establish the cause of the September incident or claim that these changes will eliminate it. Production logs, quota consumption, and the deployed revision remain unverified because the available SSH key was rejected.

GitHub documents reset-based waits for exhausted primary quotas and increasing backoff for repeated secondary throttles. REST and GraphQL have separate primary allowances; record the resource accurately even though the initial controller conservatively gates the whole installation. Use actual response evidence rather than assuming a universal quota. See [GitHub rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

## Scope and non-goals

Start with server-owned requests authenticated as a GitHub App installation. The same installation's refreshed and repository-scoped tokens share the controller state. Do not partition that state by token or repository, rotate credentials to evade a limit, or broaden token permissions.

Keep the current ten-minute background and two-minute interactive freshness policies initially. Preserve the authoritative checks before review publication and merging, including the existing merge-safety bypass of PR-sync singleflight. This plan does not change SSH provisioning, deployment credentials, GitHub App permissions, or production secrets. It does not automatically govern sandbox `gh` traffic, app-JWT requests, or user-OAuth requests whose limiting principal is different.

## Operator controls

`GITHUB_RATE_LIMIT_MODE` accepts `off`, `observe`, or `enforce` and defaults to `observe`. `GITHUB_RATE_LIMIT_INSTALLATION_ALLOWLIST` is a comma-separated list of positive GitHub installation IDs. Observation with an empty allowlist covers all resolved installation traffic; enforcement requires an explicit non-empty allowlist and affects only listed installations. An empty enforcement allowlist suppresses nothing, which prevents an accidental fleet-wide rollout. These are process configuration controls only; this implementation does not change production configuration.

The API and worker processes must use the same `ENV`, `GITHUB_APP_ID`, Redis topology, and controller protocol so they resolve the same hash-tagged key. During Redis degradation, each process uses a bounded local fallback and logs `github rate limit coordination degraded to process-local state`; this preserves request availability but cannot promise cross-process coordination. Operators should compare `_msg:"github api request"` with `_msg:"github request deferred"` on the GitHub API Health dashboard and stop expansion when `github_principal_unresolved:true` appears in covered installation traffic.

Identity attribution and controller participation are separate claims. The current server-owned inventory is:

## Implementation sequence

### PR 1: Reduce independent retries and make failure handling safe

Work primarily in `internal/services/github/retry.go`, `internal/services/github/pr_health_service.go`, `internal/services/github/telemetry/transport.go`, `internal/worker/github_retry.go`, `internal/worker/worker.go`, and `internal/worker/handlers.go`, with focused tests next to them.

1. Fix the telemetry false positive before consolidating classification. On HTTP 200, only a structured GraphQL rate-limit error can identify a request as throttled; arbitrary `data` text and generic query-complexity/node-limit errors cannot. Preserve ordinary permission-denied 403 responses as permission failures. Use the owned GraphQL decoding path for structured signals; the telemetry transport's truncated body capture is not an authoritative parser. Create the proposed `internal/services/github/ratelimit/` package in this PR to own the pure response classifier, normalized GraphQL error inputs, and typed deferral. Both the parent GitHub service and telemetry import it. Its classifier accepts HTTP status/headers and normalized error data, never the parent service's `GitHubAPIError`; `ClassifyRetry` adapts that error and handles transport failures. The new package imports neither its parent nor telemetry.
2. Give all retryable GitHub failures produced by `githubRetryableError` an explicit two-hour recovery duration, retaining the persisted `retry_window_started_at` once established. This deliberately extends the current rate-limit-only policy to transient GitHub failures; it does not change the default policy for unrelated worker errors. Throttles preserve attempts; transient failures still consume attempts and may exhaust them sooner. A job older than eight minutes with no recovery window gets one on its first GitHub retry. A job with an existing window keeps only its remaining allowance, including when errors change between throttle and transient failure.
3. Slow independent `sync_pull_request_state` retries without requiring Redis or new job columns. For a throttle without a valid timing hint, use retry slots anchored to the persisted recovery-window start: +1, +3, +7 minutes, then every five minutes (+12, +17, and so on) through the two-hour bound. Select the first future slot, schedule at the later of that slot or one minute after the current failure, then add deterministic 0–29 second jitter. This preserves the minimum wait despite request duration or timestamp precision and caps locally introduced scheduling delay at five minutes 29 seconds. Evaluate the schedule in the worker after persisting/recovering the start time, using an explicit GitHub retry-policy marker rather than error-string checks. Do not use `attempts` as the throttle counter or restart the schedule after worker restart. Valid server hints remain a lower bound; do not retry before them or beyond the recovery window. Keep review `retry_at` aligned with this final scheduling decision, not a provisional handler delay.
4. Propagate rate-limit and transient errors from the combined-status read under that explicit retry policy. Do not substitute an empty status set, remove previously known statuses, or advance successful authoritative freshness after an incomplete read. Retain the last complete projection and its freshness marker. Review other error cases separately rather than broadening this PR into a status-policy redesign.
5. Stop the reconciliation invocation's remaining GitHub calls for the affected authenticated installation after a throttle, while continuing other installations within the bounded candidate lists. Use resolved app identity or a typed controller deferral rather than a possibly stale repository installation ID; do not conflate unknown credentials. Suppress downstream merge/publication job demand only for that installation. If `reconcileSessionPublications` itself encounters the first throttle, return/defer it before `MarkFailed` or `RecordPRPublicationFailure` and stop that installation's remaining GitHub work. A throttle must not move publications to `retryable_failed` or rotate their reconciliation timestamps. Preserve ordinary publication-error handling for other failures.
6. Continue independent database-only recovery, including `ReconcileStrandedPublicationLoops`. Classify the two reconciliation outcomes separately before aggregating them. A throttle must not hide a database error, and a non-retryable GitHub error must not dead-letter retryable database recovery. Record both failures, select a bounded recoverable outcome whenever either component is retryable, and apply the GitHub deadline when its work is throttled. Do not wrap a joined tree containing `FatalError` inside a retryable result: the worker checks for fatal errors first. Test both orders of the two causes.
7. Keep existing job leases, review checkpoints, cancellation, supersession, and publication idempotency intact. Never replay a GitHub mutation transparently from an HTTP transport.

Acceptance: a fake-clock cohort of independently queued PR jobs makes fewer repeated requests during a sustained no-hint throttle than the current 60–89 second loop; demonstrate the exact before/after schedule without assuming every open PR has a queued job. One throttle also stops subsequent calls for its authenticated installation in the sweep, healthy installations and independent database recovery continue, and no publication is marked failed because it was throttled. A newly propagated transient error on a 30-minute-old job with remaining attempts receives a bounded retry. Incomplete health reads cannot become complete refreshes. This PR reduces repeated demand but does not coordinate workers or prevent the initial request burst; PR 2 supplies that coordination.

Recovery-latency acceptance: with no valid server deadline still in force and sufficient recovery-window time remaining, a job parked by a locally calculated retry must become eligible within five minutes 29 seconds after GitHub recovers. Assert this at every retry rung with maximum jitter and a recovery just after the previous failure. Measure queue delay and API execution separately; this is a bound on added scheduling delay, not total review completion time. Interactive refresh currently deduplicates against the parked job and does not advance `run_at`; PR 2's successful probe will not advance it either. The two-minute interactive stale threshold therefore remains a refresh trigger, not a recovery SLA. This explicit temporary freshness trade-off applies from PR 1 onward; increasing the local cap requires a new latency decision.

### PR 2: Wire shared installation cooldowns and durable deferrals

Extend PR 1's proposed `internal/services/github/ratelimit/` package with a small shared controller for installation-authenticated requests; add the proposed `internal/cache/github_rate_limits.go` for atomic Redis operations. The controller uses the classifier and deferral type owned by its own package and may depend on cache-owned state DTOs or primitives. `internal/cache` must not import the GitHub service, controller, or telemetry packages. The controller imports neither its parent GitHub service nor telemetry. This defines one-way dependencies for both classification and storage. Use the existing `internal/cache.Client`; do not expose its raw Redis client or create a second connection pool.

Include caller integration in this PR, not a later rollout dependency. Carry authenticated App/installation identity explicitly through `service.go`, `pr.go`, and the submitter wiring in `cmd/server/main.go`. `githubRequestMetadataForToken` currently defaults cache misses to `AuthTypeUser`; an installation token must never be relabeled as user OAuth when reverse lookup fails. Do not perform an extra GitHub lookup to identify the principal. Add an unresolved-principal counter and require zero unresolved identities in the covered installation call-path tests, including token rotation and eviction, before enforcement is available. Real user-OAuth and app-JWT calls retain their distinct classifications.

The controller must implement the following behavior:

- Before an outbound request, consult one cooldown record for the authenticated installation. If blocked, return a typed deferral carrying the next eligible time. Return promptly; do not occupy a worker or hold an HTTP request asleep until reset.
- Initially, any confirmed primary, secondary, or unknown-kind throttle pauses that installation's covered requests across REST and GraphQL. Retain resource and kind for attribution and honor primary reset deadlines. This conservative scope can delay an otherwise available resource; it avoids a multi-scope probe protocol before measurement. Other installations continue. Narrowing primary cooldowns by resource is a follow-up only if that collateral delay is material.
- Honor valid server timing hints. Without a hint, start at 60 seconds and increase secondary/unknown backoff exponentially up to a five-minute base delay, plus 0–29 second jitter. The resulting local deadline is at most five minutes 29 seconds away, matching PR 1's scheduling bound. A server deadline takes precedence over that cap. Never shorten a known cooldown. A typed controller deferral carries this exact deadline: do not apply the no-hint slot policy or add jitter a second time when the worker schedules it.
- Keep a throttle-episode counter separate from job attempts. Only the first throttle opening an episode and a throttled recovery probe advance the counter. Concurrent responses from the same episode and locally deferred requests must not each increase it.
- After a cooldown expires, admit one recovery probe per installation using an expiring lease. Other callers defer until the lease expires or its result is recorded. A success can close only the generation it probed; a delayed success must not clear newer throttle evidence. A throttled probe extends the episode. A crashed probe recovers through lease expiration. A failed probe releases its lease and advances the fencing generation without increasing the episode counter or extending the installation cooldown; it follows the caller's ordinary error policy. A complete, definitive non-throttle response can establish provider recovery while preserving any application error for the caller.
- Observe response headers as soon as they arrive. Deliver a successful response with zero remaining allowance, then defer subsequent work until reset; it cannot clear that cooldown as a successful probe. Wait for structured GraphQL error classification before treating HTTP 200 as probe success. Use PR 1's corrected classifier, preserve response bodies/close semantics, and do not promote substring-based telemetry into enforcement.
- Recognize the typed deferral in `ClassifyRetry`, `recordCodeReviewAutomaticWait`, and `codeReviewTerminalFailureStatus`; changing `RetryableError` alone is insufficient. Preserve attempts and the explicit two-hour recovery window. Schedule at the controller deadline, with matching `retry_at`, and never extend the original window. On exhaustion, preserve the last error's classification: `github_rate_limited` for a throttle/deferral or `github_unavailable` for a transient GitHub failure, both with the existing manual retry action. Do not substitute `worker_failed` or create fresh jobs automatically. HTTP request deferrals must map to an existing actionable pending/error contract, never success.
- When an actual outbound request is throttled under enforcement, propagate the controller-computed deadline as internal retry metadata alongside the original GitHub error. That deadline governs scheduling just as for a local deferral; do not also apply the slot policy or add jitter again. Keep the actual request/error in outbound telemetry. In `off` or `observe` mode, PR 1's worker policy continues to govern the real response.
- If Redis is unavailable, use bounded process-local cooldown/probe state and emit a degradation event. This fallback cannot guarantee coordination between processes. Do not turn a cache outage into a global GitHub outage or add per-request database queries.

Provide proposed `off`, `observe`, and `enforce` modes plus an installation allowlist through the existing configuration system. Default to `observe`; validate configuration values. Observation computes decisions without suppressing requests or modifying PR 1's retry behavior. Enforcement requires corrected classification, explicit principal propagation, and tested caller/wait-state integration in this same PR. Unresolved identity is a visible coverage fault, never silently counted as excluded user traffic; stop canary expansion on any such fault. This document does not change production configuration.

Acceptance: two independent controller instances sharing Redis suppress additional requests once a throttle is observed, permit recovery after eligibility, isolate unaffected installations, and survive races, token refresh, process restart, and probe failure. Real and locally deferred throttles produce matching durable job/wait timestamps and the correct terminal status. Test `sync_pull_request_state`, code-review, and publication recovery callers together. Already in-flight requests may finish; this is cooldown coordination, not a promise of zero concurrent overshoot or a global concurrency limiter.

### PR 3: Verify request attribution and prepare the canary

Complete the operational evidence and dashboard changes after PR 2 contains a usable controller and its required caller/error integration. Relevant existing files include `internal/services/github/telemetry/transport.go`, `internal/services/codereview/github_submitter.go`, `internal/worker/code_review_handler.go`, and `cmd/server/main.go`.

1. Audit explicit principal propagation for every covered call path. Observation must separately report installation requests with unresolved identity so apparent OAuth traffic cannot hide enforcement gaps.
2. Verify client construction and caller/error coverage from PR 2. Production already injects the telemetry client into the code-review submitter; preserve that wiring. Classification, principal propagation, durable deferrals, and safe publication handling are enforcement prerequisites, not deferred dashboard tasks.
3. Verify PR 2 makes reconciliation skip the blocked installation while eligible installations and independent database work continue. New ten-minute scheduler ticks must respect the same cooldown. Include overlapping scheduled/retry jobs in PR 2's integration tests; this verification must not defer essential gating until rollout.
4. Verify `waiting_for_github`, `github_rate_limited`, and `retry_at` against the actual next attempt and terminal outcome. Confirm review checkpoints prevent repeated completed publication or unnecessary restart of expensive review work.
5. Reuse the `github api request` event for actual outbound requests. Add a bounded caller category where `github_sync_reason` is insufficient, and record rollout mode/cohort and episode transitions. Emit a separate `github request deferred` event for suppressed calls; do not count those as API traffic. Never log tokens, authorization headers, or response bodies.
6. Inventory covered and uncovered clients. Keep sandbox traffic, user OAuth, and app JWT outside the enforcement claim until their ownership and quota scopes are explicitly supported. Participating API and worker processes must use the same key namespace and state protocol during a mixed rollout.

Acceptance: a review enters a timed wait on a real or synthetic throttle and resumes without duplicate side effects; actual request counts exclude deferrals; the dashboard can attribute requests and limits by installation, resource, route, caller, and sync reason. No frontend redesign is required for the existing wait state.

### Follow-up: Reduce the largest measured sources of demand

This work is conditional on evidence, not a prerequisite for the first three PRs. Compare traffic before the first throttle with traffic generated during recovery. Rank routes and callers by installation; separate REST request counts from GraphQL cost and compare observed consumption with quota deltas to identify possible uninstrumented activity.

Choose a narrow change based on the result:

| Measured source | Candidate change | Required protection |
| --- | --- | --- |
| Background health sweeps dominate useful traffic. | Allocate background work a bounded budget and prioritize active reviews/merge operations. | Demonstrate bounded background staleness and no starvation; preserve final authoritative checks. |
| Mergeability retries dominate PR-detail reads. | Measure `fetchPullRequestDetails`' four extra attempts and consider deferring unresolved mergeability through existing jobs. | Keep unknown mergeability conservative and preserve final merge checks; measure both request savings and added review latency. |
| Identical GET responses dominate. | Add conditional requests and an appropriately scoped response cache for specific supported endpoints. | Key by tenant/installation, permission scope, URL, representation headers, and API version. A 304 needs a valid matching cached body; an unknown response must never become an empty result. |
| Repeated immutable PR content reads dominate. | Reuse content identified by the exact relevant base/head revision pair and request parameters. | Head/base changes invalidate reuse; preserve authorization boundaries and publication freshness. |
| Sandbox or another uninstrumented caller accounts for the gap. | Add attribution and a separately reviewed control at that caller. | Do not claim a server-only gate fixes requests it cannot intercept. |
| Installation-wide primary cooldowns materially delay a resource with available quota. | Consider resource-specific primary gating while retaining installation-wide secondary gating. | Specify/test atomic scope precedence and probe exclusion before expanding the initial single-record protocol. |

Authenticated conditional requests returning 304 can reduce primary quota usage, and webhook-driven updates can avoid polling. Endpoint support and correctness must be verified before adopting either optimization. See [GitHub REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api). Do not broadly lengthen polling intervals, tune alerts, or add a global concurrency limiter without evidence that the relevant behavior is causing the problem.

## Database schema

No database migration is planned for PRs 1–3. Existing durable job fields `run_at`, `attempts`, and `retry_window_started_at` remain the source of truth for scheduling and retry limits. Continue updating existing code-review wait metadata through `SetWaitingForGitHub` in `internal/db/code_reviews.go`. Preserve all organization filters and lease ownership checks.

Proposed Redis runtime state is separate from durable jobs and is not insert-only versioned configuration:

| Key/state | Contract |
| --- | --- |
| Namespace | One record per application/environment, GitHub App ID, and installation ID; proposed key `{ghrl:v1:<env>:app:<appID>:inst:<instID>}:state`. No token, repository, or organization suffix that would split a shared installation quota. |
| Scope | One installation-wide gate initially; retain validated provider resource identifiers as attribution, not independent cooldown keys. |
| Fields | Integer generation and episode count; UTC millisecond `blocked_until`; typed limit kind; resource attribution; bounded reason; probe lease owner, unique per-claim token, generation, and `probe_until`. Cache DTOs/primitives are owned by `internal/cache`. No tenant content or credentials. |
| Atomicity | Add atomic Lua operations inside `internal/cache` for deadline extension, episode transitions, and probe claims/completion. The package has no existing Lua primitive to reuse. Operate on one installation record, use max deadlines and generation-checked completion, and test support for the configured Redis Cluster topology. Any future additional keys used in one script must retain the same installation hash tag. |
| Expiration | Retain episode state beyond its cooldown through the supported retry window; leases expire independently. TTL must never expire before a server-provided deadline. Bound the number and lifetime of process-local fallback entries. |

Redis coordination can span organizations that share a GitHub installation because it represents provider quota, not access to tenant data. Existing service authorization and database tenant isolation remain unchanged; do not expose this shared state through tenant APIs. If implementation discovers a durable schema requirement, revise this plan explicitly before adding one.

The single-record choice keeps atomic operations within one Redis Cluster slot; hash tags preserve that placement if related keys are added later. See the [Redis Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/). Cache failover can lose recent state, so coordination remains best-effort acceleration over durable job retries, not a strict global request-count guarantee.

## API contract

No new public routes, methods, request parameters, response shapes, RBAC rules, or SSE payloads are planned. Existing review status responses retain their wait phase, status code, and next retry time. Audit synchronous callers during PR 2 before enabling enforcement; if their existing error contracts cannot express deferral, record and review the specific API change before implementing it.

The proposed internal controller takes an authenticated request scope and returns either permission to attempt one request or a typed deferral with kind, installation, deadline, and generation. Response observations update that state. Use typed enum values and validation for new enum-like fields; keep credentials out of controller keys, errors, and logs. `ClassifyRetry` must recognize typed deferrals through wrapping and classify them as retryable/rate-limited for both worker scheduling and code-review status helpers. The worker adapter preserves the recovery-window bound and sets `ConsumeAttempt=false`.

PR 1 also introduces an internal typed retry-policy marker for no-hint GitHub scheduling. The worker computes the final `run_at` after establishing the persisted window and before checking whether the wait fits inside it. Move automatic-wait persistence out of the provisional handler calculation into a narrowly scoped retry-scheduled hook: after the lease-owned job retry update succeeds, pass that exact `run_at` to code-review wait persistence. Register this alongside existing job hooks and use their detached, timeout-bounded context precedent; do not update wait metadata on lost leases or an exhausted retry. Log a status-persistence failure while retaining the already scheduled job. This keeps the job and `retry_at` on the same schedule without a new public API or schema. HTTP transport code must not enqueue jobs or retry mutations on its own.

## Validation and acceptance

The entries below define the implementation validation contract; completed local evidence is recorded in Progress and Outcomes. Use fake clocks and deterministic jitter for focused tests, table-driven cases, parallel isolated fixtures, and exact assertions. Avoid real-time sleeps except for the explicit HTTP-client timeout integration regression.

| Scenario | Required result |
| --- | --- |
| Primary 403/429 with remaining=0 and reset. | Wait until the server deadline; another installation continues. Both resources in the affected installation initially wait, with that collateral delay visible in observation. |
| Secondary 403/429 with seconds/date Retry-After or no hint. | Respect valid timing; increase no-hint delay across failed probes; ordinary authorization 403 remains a permission error. |
| GraphQL HTTP 200 with a structured rate-limit error. | Enter the appropriate cooldown; unrelated successful data containing similar text is not classified as throttling. The owned complete-envelope decoder remains authoritative when the error or a successful probe appears after more than one MiB of data; transport observation memory stays bounded. |
| Successful last request consumes the remaining allowance. | Return success and defer subsequent work; do not mark the successful request as a failure. |
| Reconciliation throttles or a combined-status read fails transiently, including an interrupted or timed-out HTTP 200/429 body. | Preserve response status, headers, controller metadata, read failure, and caller-context provenance together. An HTTP-client body timeout with a live caller is retryable; caller cancellation/deadline remains terminal. Stop affected GitHub work, preserve last complete projection/freshness, run independent database recovery, and retain both errors if recovery also fails. |
| Many queued PR-sync jobs repeatedly receive no-hint throttles. | PR 1 follows the exact increasing slot schedule across worker restarts and preserves attempts; compare request counts with the current fixed-delay baseline. PR 2 additionally prevents outbound attempts during the shared cooldown. |
| GitHub recovers just after a no-hint throttle at any retry rung, with adequate recovery time left. | The parked job becomes eligible within five minutes 29 seconds, including maximum jitter, under both PR 1 and PR 2. Interactive dedupe does not reset or shorten its delay. Separately measure queue/runtime overhead; retain valid server deadlines even when they exceed the local bound. |
| Old job hits its first transient GitHub failure, or throttle and transient errors alternate. | Persist an explicit bounded window on first retry; preserve it thereafter and consume attempts only for transient failures. No immediate failure solely because `CreatedAt` is older than eight minutes; no window reset on error-type changes. |
| Throttle inside publication recovery; non-retryable GitHub error joined with retryable database recovery, in either order. | No throttle-induced `MarkFailed`/publication failure metric; independent recoverable work is retried and both causes are recorded without a nested fatal wrapper overriding the result. |
| Multiple jobs/clients observe the same throttle. | One episode increment, no request while known blocked, and at most one recovery probe for the affected scope. Locally deferred work does not amplify backoff. |
| Late responses, new tokens, process restart, or probe crash. | A failed release advances only the fencing generation, preventing peers from restoring the released lease. A fenced response with a strictly later future provider reset or Retry-After can extend an active cooldown and invalidate its current probe without advancing the episode or generation. ## Surprises & Discoveries

- July fixes already addressed CI-event refresh amplification and redundant synchronization. Their presence changes the starting point for this investigation.
- The ordinary scheduled batch volume is bounded; it is insufficient evidence by itself to blame polling for the September recurrence.
- Combined-status fetch errors can be swallowed, so recovery work must also preserve authoritative-read completeness.
- Independent per-PR jobs can continue retrying even when an organization sweep stops. Their actual production volume remains unknown.
- A transient retry without an explicit window uses job creation time; the two-hour window previously applied only to rate limits.
- Telemetry substring classification, publication `MarkFailed`, and cache-miss auth attribution are unsafe defaults for the new enforcement path and require explicit handling.
- Production submitter instrumentation is injected at server wiring; its default client alone would give a misleading coverage assessment.
- Real standalone/Cluster Redis verification exposed that a recovered shared record could leave a stricter process-local fallback behind. Recovery now writes a generation-preserving tombstone so every participating controller can discard stale local state safely.
- Repository installation IDs can be stale even when token resolution succeeds through the integration record. Resolutions now retain the exact issuing installation ID, and covered request context is attached after resolution rather than inferred from token-cache membership.
- Observe-mode cooldown predictions and enforce-mode suppression need distinct telemetry even though they share the same controller decision path. `github_request_suppressed` makes that distinction without counting either event as outbound traffic.
- Initially broad worker and API-handler race runs exposed unrelated timing-sensitive lifecycle tests: a mocked worker poll could lose a cancellation race, and a session-stream test deliberately closed Redis while asserting a retry event. The reproducible focused target now runs every changed worker regression and representative changed API GitHub caller paths under `-race`, while `go vet` still covers the complete touched packages.
- Round-two review found that identity attribution alone could make two API clients appear covered while they bypassed the controller, and that an expired probe reclaimed by the same process needed a unique claim token in addition to generation and owner fencing.
- A controller must hydrate its bounded local fallback from an authoritative Redis read, not only its own writes; otherwise a Redis outage immediately after learning another process's episode could lose that episode's recovery-probe state locally.
- A bounded transport prefix cannot be the authoritative GraphQL parser. A request-scoped handoff from the existing full-envelope decoders preserves bounded observation memory while covering suffix errors and oversized successful recovery probes.
- Running post-schedule UI hooks after the job lease is released requires a database-level fence against the exact pending transition; checking review status alone can resurrect an obsolete wait after a newer attempt starts.
- A healthy Redis connection does not imply its cooldown record survived restart or rollback. Controllers must atomically restore retained newer local evidence before observe, claim, or completion, while allowing current-generation tombstones and newer shared probe tokens to win.
- Full-envelope GraphQL classification can remain allocation-bounded even when callers already own a multi-megabyte response: validate and scan the complete JSON structure by byte offsets, then decode only the structured `errors` value instead of copying `data` into `json.RawMessage`.
- Restoring a stronger same-generation deadline must revoke any probe admitted against the rolled-back shorter deadline. Preserving its token would let a late success erase authoritative future cooldown evidence; the restored block itself provides exclusion until a fresh probe is eligible.
- Stuck PR-action reconciliation is database-only recovery, unlike the merge-when-ready queue sweep whose jobs perform fresh authoritative GitHub work. The former must still run after an installation throttle; the latter remains suppressed only for the affected authenticated installation to avoid creating more GitHub demand while healthy installations continue.
- Redis generation fences probe outcomes, but cannot by itself invalidate a later unexpired server deadline retained by another controller. Cross-generation reconciliation now keeps the newer generation, merges only stronger future deadline evidence, and revokes probes admitted against the weaker state; completion tombstones remain authoritative.
- A response-body read can fail after HTTP status, provider timing, and controller retry metadata are already known. Returning the raw read error discarded those signals, so interrupted GitHub responses now carry both the read cause and the response metadata and cannot produce an authoritative health projection.
- Go's `http.Client.Timeout` can expire while reading a response body without expiring the operation context supplied by the caller. Since both client timeouts and caller deadlines match `context.DeadlineExceeded`, retry classification must retain the caller context's actual terminal state rather than infer provenance from the timeout error alone.
- No successful production log or database query was obtained during this investigation.
