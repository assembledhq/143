## Purpose and observable outcome

A reviewer must receive the captured PR comparison and available repository preparation outputs before it begins inspecting code. A review may withhold approval for uncertainty only when it identifies specific missing evidence, explains how that evidence could materially change the approval decision, and states what would resolve the gap. The author sees that explanation in the GitHub review and dashboard.

Workspace preparation failures are operational failures, not confirmed code defects. Some evidence cannot be obtained from a checkout: production migration coverage, another service's behavior, unpublished stack changes, and external data may still require human evidence. Making dependency source available does not establish runtime behavior or test success.

## Surprises & Discoveries

- `DockerProvider.CloneRepo` uses `--filter=blob:none`, then removes the installation token from the origin URL. The checkout contains head files, but reading historical file contents may still require an authenticated fetch.
- `PrepareCodeReviewWorkspace` closes its credential socket before transferring the prepared container. Reviewer execution must reopen the socket. Comparison evidence should not depend on that later handoff.
- Session revision context already captured `base_sha`; the prior agent checkout context read only the PR number and head SHA.
- Minimal review preparation skipped both supported declared dependencies and repository bootstrap. A configured dependency install could therefore exist but never run for a review.
- Prior shared-container readiness verified branch/head, which could become true before dependency or evidence preparation finished.
- A bare uncertainty boolean previously passed synthesis validation. The generated explanation did not become a structured risk subject, and blocked reviews suppressed the general model-written review summary.
- The existing risk-reason JSON already supports a `subject` string. Concrete uncertainty explanations can reach existing API/dashboard consumers without a database migration or a new endpoint.
- Unfenced valid synthesis JSON with nested objects was incorrectly extracted from the last opening brace. Preserving the complete valid JSON is necessary for the new reason objects and existing nested findings.
- Cross-process preparation needs a sandbox-local kernel lock. A server-process mutex does not serialize separate executors, and timeout cleanup must terminate the entire subprocess group before releasing that lock.
- A preparation wrapper carrying an authenticated hydration script in its arguments exposes the installation token to repository-defined setup and verifier children. Log redaction alone cannot close this disclosure; private input and separately scoped authenticated children are required.
- Removing inherited/global Git configuration does not neutralize repository-local transport settings. A repository command can plant URL-scoped proxy/TLS settings and remove comparison objects, then a later warm hydration can expose its transient header. Validate a finite platform-created local configuration and physical repository metadata before authentication and after repository commands.

## Recipe/config audit gate

Run `make audit-review-recipes AUDIT_MANIFEST=/private/path/inventory.json` before this rollout. Capture all repositories with reviews enabled across the worker's rollout scope; an arbitrary subset cannot establish release readiness. The offline CLI checks the supplied inventory and cannot discover omitted repositories, so a fresh complete enablement capture is a separate release prerequisite. It emits deterministic JSON, exits 0 only when every explicit target passes, exits 1 for open recipe/config gates, and exits 2 for invalid invocation or inventory; Make propagates failure as a nonzero result. It never runs bootstrap or fetches repository content. Keep live inventories, owner assignments, and review evidence outside this public checkout.

The version-1 JSON inventory contains `repositories`, each with `repository`, full Git `revision`, `config_present`, exact `config_json` snapshot text, `config_sha256`, `owner`, and `required_evidence`. Supported categories are `git`, `javascript_dependencies`, `go_dependencies`, `python_dependencies`, `ruby_dependencies`, `generated_artifacts`, `submodules`, `lfs`, and `external_caches`. Capture the config at the stated revision; an absent config uses empty text and its SHA-256. The audit checks syntax, setup schema, supported tool recipes/pins, owners, and required coverage. It reports effective review command counts, verifier counts, and declared paths/categories without exposing command bodies. `preview` remains opaque and does not count as review setup.

Any effective review setup, or any non-Git evidence requirement, needs `recipe_review` with matching `revision` and `config_sha256`, a nonempty `evidence` reference, `preserves_tracked_files: true`, `setup_only: true` (no tests, builds, or services), and explicit `covered_evidence`. Each non-Git category also needs matching `review.evidence` paths and local verification commands. Legacy bootstrap commands without an explicit `review` section close the audit gate even with a valid Git-only attestation: they cannot reuse readiness and would rerun for each reviewer under the original deadline. An empty `review` object can explicitly disable bootstrap for Git/tool-only review. An owner/review is not inferred from command presence. A reviewed Git-only repository can have no setup; a tracked/vendor source recipe can declare verification and evidence without a setup command. Invalid config cannot establish partially decoded coverage. Readiness here means reviewed declarations at a captured snapshot, not installed artifacts or approval of unpublished recipe edits.

## Contracts and compatibility

There is no new HTTP endpoint or status enum. Migration 000310 adds a concurrent partial expression index supporting the durable preparation-budget lookup by tenant, review, and session; apply it before enabling the new query at rollout. No existing lifecycle columns change. Existing assessment/agent-result JSON stores the structured synthesis, while existing risk-reason objects carry the author-facing explanation in `subject`. Existing API authentication, tenant scoping, publication receipts, and deterministic approval safeguards remain applicable.

Setup failures reuse existing failed-review metadata, safe status messages, assessment failure details, and terminal rolling comments. Failure provenance is scoped to the current tenant/review/session/generation and projected by the controller. Raw commands, tokens, and stderr are not author-facing failure evidence. Setup failure cannot produce an approval, an uncertainty blocker, or a new formal code-defect review.

Transient source-transport errors can retry within the original preparation checkpoint. Failed dependency/bootstrap commands, malformed inputs, cancellation, and exhausted budgets remain terminal. A finite moved-head signal reaches bounded live synchronization before operational failure projection. Confirmed new heads use the existing replacement-review flow; unresolved API lag expires into stale status under an atomic tenant/review/session/head/generation/publication fence. Runtime dead-letter reconciliation retains the original signal generation and cannot adopt a newer workspace.

The synthesis contract adds explicit uncertainty reasons. Every new prompt emits that field, including an empty array when no uncertainty remains. The parser and restored-result usability checks enforce consistency. A historical false flag without the new array may remain usable; a historical true flag without a complete reason cannot satisfy the new contract. Historical review output still renders its fallback explanation.

The current recheck planner treats prompt-only changes as eligible for an evidence-only recheck. The reason validator guards incompatible historical uncertainty directly; this patch does not force a new full review of every compatible historical clean result.

The optional `review` config contains bounded command arrays, local `verify_commands`, and `evidence` entries with canonical workspace-relative `path`, `description`, and a typed `category`. Presence overrides ordinary bootstrap only in authoritative review mode; an empty object intentionally selects Git/tool-only setup. Ordinary coding and preview setup retain their behavior. Evidence roots reject metadata/credential locations, escaping symlinks, unsupported filesystem objects, and dependency directories without regular files. Reviewer prompts expose the config as untrusted source-location data, never as approval instructions.

The version-2 readiness receipt binds to the captured comparison and exact config. It records only declared-root manifests of path/type/size/safe-link metadata and verifies local Git blobs and supported tool pins. An unrelated JavaScript output cannot mask a missing Go/Python cache. A bounded safety traversal rejects unsafe roots and entries before any repository commands. Fresh setup runs declared verifiers and checks clean tracked source before recording success; warm reuse remains provisional until verification succeeds and a complete post-verifier manifest matches the saved evidence. The tracked-source check must use an owned temporary index from the pinned head, comparing Git content and tracked modes independently of the checkout's writable index. Normal conversions in tracked `.gitattributes` remain supported; mutable local attributes overrides are rejected. This avoids redundant full inventories without weakening the final comparison. Legacy or incomplete artifact recipes still prepare but cannot reuse dependency readiness. Old or non-object receipts invalidate safely. No receipt proves test success or hashes every dependency byte; same-sized content corruption remains outside platform manifest guarantees.

Expired preparation can use a separate bounded 60-second allowance for platform-only verification of an existing receipt. It cannot run repository verifier/setup commands, acquire an installation token, fetch, repair, or replace readiness. Review Git operations disable repository hooks through a transient `core.hooksPath=/dev/null`; verification also neutralizes configured clean/process filters and disables fsmonitor, external diff, and text conversion. Pinned comparison trees must be local before a worktree check can run. The allowance does not extend the preparation budget. Locked source recipes perform their own input/artifact checks and have offline verification paths that never resolve, download, or execute dependency/project code. Their complete file inventories include JavaScript implementation and Go assembly sources, so a partial cache cannot pass setup's early reuse check and receive a degraded replacement receipt. Snapshot inclusion already covers `.143/cache`, so no snapshot format changes are needed.

Review authentication uses private stdin consumed before child dispatch. The public recipe fields contain no installation token. Input reading observes the original deadline and cancellation, is size bounded, and closes its descriptor before subprocesses. The controller uses isolated absolute Python and an absolute shell; trusted Git stages use system executables and an owned environment without inherited Git command configuration or tracing. Scoped HTTP authentication is available only to the trusted Git child, with clean remote URLs, disabled credential helpers/maintenance, and no authenticated worktree checkout. Repository setup and verification use their ordinary tooling paths without inheriting that authentication or private input. Healthy warm reuse and local dependency repair do not request a token; only missing pinned trees request bounded hydration. Expired verification never requests one.

Trusted source validation owns its subprocess search path as well as its direct Git executable. This matters because Git can invoke internal subprocesses. Review-only bootstrap invokes the image's absolute integration helper under that path; repository recipes retain their ordinary tooling paths. Full object validation keeps multi-pack-index verification enabled, disables commit-graph acceleration, and rejects unsupported commit-graph metadata. It does not store a sandbox-written object inventory or require a new readiness receipt version.

The local-config integrity contract requires trusted scoped repository metadata even for warm and expired checks, without requesting a token or contacting the source remote. Parse the literal `.git/config` with includes disabled and a neutral working directory. Allow only exact clone values, a trusted origin URL and fixed fetch refspec, validated origin branch entries, optional user identity, and the platform bootstrap's helper and push setting. Reject unknown/duplicate keys, transport or executable overrides, config includes, and metadata layouts that can redirect discovery through `.git` pointers, shared configuration, or object alternates. Reject grafts and replacement refs that can alter comparison identity. Warm readiness probes must read bounded regular HEAD/ref metadata without consuming Git configuration; the guarded evidence barrier then validates the pinned checkout. Fresh, warm, and restored review bootstrap must pass the bounded guard before its own Git config writes. Inspect under the preparation lock before missing-object detection, before each authenticated child, and after repository commands before readiness or reuse. Fetch through the validated origin to avoid creating anonymous remotes, and force HTTP proxy/verification defaults while removing ambient CA/proxy overrides; do not configure invalid empty certificate paths. Cancellation markers live outside rejected Git metadata. These checks consume the existing deadline or expired-verification allowance. A failed integrity check is an operational setup failure and cannot request hydration or establish a receipt.
