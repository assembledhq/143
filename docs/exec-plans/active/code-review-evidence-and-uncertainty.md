## Purpose and observable outcome

A reviewer must receive the captured PR comparison and available repository preparation outputs before it begins inspecting code. A review may withhold approval for uncertainty only when it identifies specific missing evidence, explains how that evidence could materially change the approval decision, and states what would resolve the gap. The author sees that explanation in the GitHub review and dashboard.

Workspace preparation failures are operational failures, not confirmed code defects. Some evidence cannot be obtained from a checkout: production migration coverage, another service's behavior, unpublished stack changes, and external data may still require human evidence. Making dependency source available does not establish runtime behavior or test success.

## Surprises & Discoveries

- `DockerProvider.CloneRepo` uses `--filter=blob:none`, then removes the installation token from the origin URL. The checkout contains head files, but reading historical file contents may still require an authenticated fetch.
- `PrepareCodeReviewWorkspace` closes its credential socket before transferring the prepared container. Reviewer execution must reopen the socket. Comparison evidence should not depend on that later handoff.
- Session revision context already captured `base_sha`; the prior agent checkout context read only the PR number and head SHA.
- Minimal review preparation skipped both supported declared dependencies and repository bootstrap. A configured dependency install could therefore exist but never run for a review.
- Prior shared-container readiness verified branch/head, which could become true before dependency or evidence preparation finished.
- A bare uncertainty boolean previously passed synthesis validation. The generated explanation did not become a structured risk subject, and blocked reviews suppressed the general model-written review summary.
- The existing risk-reason JSON already supports a `subject` string. Concrete uncertainty explanations can reach existing API/dashboard consumers without a database migration or a new endpoint.
- Unfenced valid synthesis JSON with nested objects was incorrectly extracted from the last opening brace. Preserving the complete valid JSON is necessary for the new reason objects and existing nested findings.
- Cross-process preparation needs a sandbox-local kernel lock. A server-process mutex does not serialize separate executors, and timeout cleanup must terminate the entire subprocess group before releasing that lock.
- A preparation wrapper carrying an authenticated hydration script in its arguments exposes the installation token to repository-defined setup and verifier children. Log redaction alone cannot close this disclosure; private input and separately scoped authenticated children are required.
- Removing inherited/global Git configuration does not neutralize repository-local transport settings. A repository command can plant URL-scoped proxy/TLS settings and remove comparison objects, then a later warm hydration can expose its transient header. Validate a finite platform-created local configuration and physical repository metadata before authentication and after repository commands.
